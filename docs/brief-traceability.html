Drafting the note
1 Give the reviewer a draft note for each exception
Give a reviewer the evidence and a draft discrepancy note needed to resolve an exception.Overview
 When reconciliation marks an invoice discrepant The batch (cli.py) drafts the note while it reconciles. Invoices that are not discrepant get no note. ✅ Implemented
2 Use the model to draft it
Use the model to draft a short discrepancy note from verified findings and source references.Analytics & Insights
 During the batch; also on a correction, and on first view if no note exists yet Bedrock (Sonnet 4.5) drafts it. If the model is unavailable, a calculated note is used, and the page always says which: drafted_by = model or calculated. ✅ Implemented
3 Only from verified findings
from verified findingsAnalytics & Insights — same line as #2
 Every draft, before it is stored The model gets only the three computed figures. verify_note rejects the whole draft on any other figure, a wrong PO, the wrong direction or rounding. Up to 3 attempts, telling the model why, then the calculated note. ✅ Implemented
4 Cite the source records
drafts a review note citing the source records.Overview — example behaviour
 Every draft Verification requires the invoice number and the matched PO ID in the text. The (i) icons cite the image, the model, the PO and receipt rows, and the matching rule. ✅ Implemented
5 Do not imply wrongdoing
do not treat a discrepancy as proof of wrongdoing.Analytics & Insights
 Every draft Verification rejects cause or blame words (overcharge, error, mistake, fraud, wrongly, deliberately and others). A test checks the calculated note against the same list. ✅ Implemented
6 Notes are only drafts
All notes remain drafts; accounting integrations, payment execution, authentication, and cloud deployment are unnecessary.Technical Implementation
 Always No send control anywhere; the heading reads “(draft)”. The reviewer edits the note and decides what to do with it. ✅ Implemented
Corrections
7 Correct a value and rerun reconciliation
Let a reviewer correct an extracted value, rerun reconciliation, and save the review state.Dashboard/Visualization
 When the reviewer saves a correction One transaction: an append-only corrections row, current_value updated, then recalculate_one. The route holds no reconciliation logic. ✅ Implemented
8 Keep the original extraction visible
Keep the original extraction available so the correction can be understood.Dashboard/Visualization
 Always, after any correction original_value is never overwritten. A corrected field’s (i) shows the whole chain: v0 extracted → v1 → v2 (current). ✅ Implemented
9 The correction updates the saved result and survives a restart
Correcting an extracted field reruns reconciliation, updates the saved result, and remains visible after restarting the app.Minimum demonstration
 On the correction, and on any later restart Results, corrections and note versions are stored in SQLite; nothing is held only in memory. Checked across two separate server processes. ✅ Implemented
10 What happens to the note after a correction
Not stated. Follows from “from verified findings” (#3) and “updates the saved result” (#9).Our reading of Analytics & Insights + Minimum demonstration
 When a correction changes the figures Still discrepant and a figure the note states changed → redraft as a new version. Nothing the note states changed (e.g. a SKU fix) → keep the note; no model call. Reviewer had edited it → keep the edit, flag it as describing old figures. No longer discrepant → retire it: editor hidden, edits refused (409), history kept. 🟡 Add to README “Settled ambiguities”
